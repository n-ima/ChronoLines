# 詳細設計: フォーム・ダイアログ・リカバリ画面

対応要件: US-001/003/009/010/011。見た目の正: [../ui/screen-03-forms.html](../ui/screen-03-forms.html)。

共通仕様: モーダルダイアログ（オーバーレイ + Esc/〔キャンセル〕で閉じる。編集中に閉じる
場合は破棄確認）。検証はフィールドの blur と送信時に行い、エラーはフィールド直下に
インライン表示する。検証規則・メッセージは data-model.md 7章と domain-logic.md
`parseYearInput` が正（同じ関数を使う）。

## 1. 人物フォーム（US-001）

- 開く動線: ツールバー〔＋人物〕（新規）/ 人物列の行クリック → 行メニュー〔編集〕。
- フィールド: 名前*（text）/ 生年*（year text: 前100・-100・1600 を受理）/
  生月・生日（select、任意。日は月選択時のみ活性）/ 没年・没月・没日（同・任意）/
  タグ（下記のタグピッカー）。

### タグピッカー（人物フォーム・イベントフォーム共通の部品）

- 構成（上から）: (1) 付与済みタグの色付きピル（✕で除去）、
  (2) **「登録済みタグから選択」** — `allTags` の未付与タグを色付きピルで一覧表示し、
  クリックで付与（登録済みを選ぶのが第一の動線）、
  (3) **新規タグの入力欄** — 入力して Enter で新規作成・付与
  （入力中は既存タグの部分一致サジェストを出し、既存を選べば新規作成しない。
  前後空白は trim、同名の重複付与は無視）。
- タグの色はタグ名から決定的に導出する（design-tokens.md のタグ配色・割り当て規則）。
  同名タグはアプリ全体で常に同じ色になる。
- 検証（エラーID → メッセージ）:
  - E-P-NAME-EMPTY → 「名前は必須です」
  - E-YEAR-FORMAT → 「年の形式が正しくありません（例: 1600、前100、-100）」
  - E-YEAR-ZERO → 「0年は存在しません（前1年の翌年は西暦1年です）」
  - E-P-DEATH-BEFORE-BIRTH → 「没年は生年以降にしてください」（受け入れ条件: 生年1600・没年1550 は拒否）
  - E-DAY-WITHOUT-MONTH → 「日を指定する場合は月も指定してください」
- 保存 → ミューテーション（addPerson/updatePerson）→ 自動保存。生年編集時は
  セルが都度計算のため全セルの年齢が自動で再計算される（US-001 受け入れ条件）。

### 人物の削除（US-001 の確認フロー）

- 行メニュー〔削除〕→ 紐付く個人イベントの有無で分岐:
  - **あり**: 選択ダイアログ「『徳川家康』に紐付くイベントが3件あります」
    〔イベントも削除する〕〔紐付けを解除してイベントは残す〕〔キャンセル〕
    → 選択に応じ `deletePerson(id, 'deleteEvents' | 'unlink')`。
  - **なし**: 確認ダイアログ「『◯◯』を削除しますか？」〔削除〕〔キャンセル〕。

## 2. イベントフォーム（US-003）

- 開く動線: ツールバー〔＋イベント〕/ サイドパネルのイベント行〔編集〕/
  年ヘッダー右クリックメニュー〔この年にイベント追加〕（年を初期値に）。
- フィールド: イベント名*（text）/ 年*（year text）/ 月・日（select、任意）/
  メモ（textarea 2000字）/ 人物への紐付け（select: 「なし」+ 人物一覧、任意）/
  タグ（人物フォームと同じタグピッカー。2026-08-12差分でイベントにもタグ付与可）。
- 検証: E-E-NAME-EMPTY「イベント名は必須です」、E-YEAR-*、E-DAY-WITHOUT-MONTH
  （年空欄で登録 → エラーが受け入れ条件）。
- 削除: フォーム内〔削除〕→ 確認ダイアログ。

## 3. 年表管理ダイアログ(US-009)

- 開く動線: ツールバー左端の年表切り替えドロップダウン →〔年表の管理...〕。
  ドロップダウン自体で切り替え（switchTimeline）は1クリックで完了する。
- 一覧表示: 年表名・人物数・イベント数・〔切替〕〔名前変更〕〔削除〕。
- 〔＋新しい年表〕: 名前入力（E-T-NAME-EMPTY「年表名は必須です」）→ 空の年表を作成し切替。
- 〔削除〕→ 確認ダイアログ「年表『戦国』を削除しますか？ 人物12人・イベント34件も
  削除されます。この操作は取り消せません」〔削除〕〔キャンセル〕（受け入れ条件:
  承諾しなければ削除されない）。最後の1つを削除したら空の「年表1」を自動作成（data-model.md 3章）。

## 4. エクスポートダイアログ（US-011）

- 開く動線: ツールバー〔入出力〕→ タブ〔エクスポート〕。
- 範囲選択: （・）現在の年表のみ （・）すべての年表 → 〔JSONをダウンロード〕。
- 生成はクライアント単独で行う（Blob + a[download]。サーバー死亡時でも動作する退避手段。
  ADR 0002）。形式は data-model.md 6章。

## 5. インポートダイアログ（US-011）

- 動線: 〔入出力〕→ タブ〔インポート〕→ ファイル選択（.json）。
- 手順: (1) 読み込み・検証（エクスポート形式 or 保存形式を自動判別。旧版は移行、
  data-model.md 6章）→ (2) 内容プレビュー「年表2個・人物150人・イベント420件
  （エクスポート日時: …）」→ (3) 取り込み方法の選択:
  - （・）**すべて置き換える** — 現在の全データをファイル内容で置き換える（復旧手順。
    受け入れ条件「エクスポート→全削除→インポートで復元」はこの経路）
  - （・）**年表として追加する** — ファイル内の年表を新しい年表として追加（id再採番）
  - 置き換えの場合は追加確認「現在のデータはすべて失われます。よろしいですか？」
- エラー（既存データは無変更のまま表示）:
  - E-IMPORT-INVALID → 「このファイルは取り込めません（形式が正しくありません）」+ detail
  - E-IMPORT-NEWER → 「より新しいバージョンのアプリでエクスポートされたファイルです。アプリを更新してください」
  - 壊れたJSON → E-IMPORT-INVALID（受け入れ条件: エラー表示・既存データ無傷）

## 6. リカバリ画面（US-010。通常UIの代わりに全画面表示）

GET /api/store が E-STORE-CORRUPT / E-STORE-NEWER のとき、グリッドを描画せずこの画面を出す。

- **E-STORE-CORRUPT（保存データ破損）**:
  - 表示: 「保存データを読み込めませんでした」+ detail + データファイルのパス。
  - 説明: 「既存のファイルは変更されていません。次のいずれかで復旧できます」
    1. 〔JSONファイルから復旧（インポート）〕→ 5章のインポート（置き換えのみ・
       `recovery: true` で PUT。サーバーが破損ファイルを改名保全してから書き込む）
    2. バックアップからの手動復旧手順の提示: 「`chronolines.json.bak` を
       `chronolines.json` に上書きコピーして〔再試行〕」（パスを明示）
    3. 〔空のデータで開始〕→ 追加確認の上、初期ストアを `recovery: true` で保存
  - 〔再試行〕ボタン（ファイルを手で直した後の再読込。サーバーの再読込APIは設けず
    ページリロード + サーバー再起動案内で行う → 起動時判定のため。画面に
    「修復後はサーバーを再起動してから再試行してください」と明記する）。
- **E-STORE-NEWER（未知の新バージョン）**:
  - 表示: 「このデータはより新しいバージョンの ChronoLines（形式v2）で保存されています。
    このバージョン（形式v1）では開けません」+ データファイルのパス。
  - 説明: 「データを守るため、このままでは一切書き込みません。アプリを新しいバージョンに
    更新してから開いてください」。書き込み系の操作はすべて不可（US-010「上書きせず停止」）。

## 7. エラーメッセージの原則

- 何が起きたか + データがどうなっているか（無傷/保全済み）+ 次にできることを必ず書く。
- 技術的 detail（Zod issue・OSエラー）は折りたたみ表示で添付する（監視なしの
  ローカルアプリでは画面が唯一のログのため。nfr.md 運用・監視）。
