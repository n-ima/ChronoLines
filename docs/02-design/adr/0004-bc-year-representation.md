# ADR 0004: 紀元前の年の内部表現（保存/入出力は符号付き年、計算は天文学的年数）

- 日付: 2026-08-12
- ステータス: 承認済み

## コンテキスト

- 生年・没年・イベント年・範囲指定に紀元前の年を受け付け、「前500」形式で表示する。
  紀元0年は存在しない（前1年の翌年 = 西暦1年）。0年の入力は拒否する（US-005）。
- 年齢計算・年の全順序は glossary.md「満年齢」に定義済み（例: 前100年生まれ →
  西暦1年のセルは 100、前50年のセルは 50）。
- 列インデックス計算・10年単位の集約（US-007）・範囲の自動決定（US-006）には
  連続した整数軸が必要。「0が存在しない符号付き年」のままでは全演算に例外分岐が入る。

## 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| A: 全レイヤで符号付き年（前N = -N、0は不正値） | 保存JSON・入力値が人間の直感（前100 = -100）と一致し、目視デバッグ・手書き編集が容易 | -1 の次が +1 という不連続軸のため、年齢・列位置・10年境界のすべての計算に「0を飛ばす」分岐が散らばり、バグの温床になる |
| B: 全レイヤで天文学的年数（前1年 = 0、前2年 = -1、…前N = -(N-1)） | 整数軸が連続し、年齢 = 差、列 = オフセットの単純算術になる | 保存JSONの「-99」が「前100年」を意味することになり、人間が読み書きするファイル・エクスポートJSONとして誤読を誘発する（US-011 の手動復旧と相性が悪い） |
| C: 境界で使い分け（保存・入出力 = 符号付き年 / 計算 = 天文学的年数） | 両者の利点を取れる。変換は `astro = y < 0 ? y + 1 : y` の1行 | 変換の掛け忘れ・二重変換のリスク。変換箇所を1モジュールに閉じ込める規律が必要 |

## 決定

**選択肢 C** を採用する。

- **保存データ（JSON）・エクスポート/インポート・フォーム入力値・URLや設定値**:
  符号付き年 `StoredYear`（西暦Y = Y、前N = -N。**0 は不正値として Zod で拒否**）。
- **内部計算（年齢・列インデックス・範囲・10年境界）**: 天文学的年数 `AstroYear`
  （前1年 = 0、前N = -(N-1)）。変換は次の2関数のみ:
  - `toAstro(y: StoredYear): AstroYear = y < 0 ? y + 1 : y`
  - `fromAstro(a: AstroYear): StoredYear = a <= 0 ? a - 1 : a`
- **満年齢 = `toAstro(表示年) - toAstro(生年)`**。この1式が glossary.md の場合分け
  （西暦同士 Y−B / 紀元またぎ Y+B−1 / 紀元前同士 B−C）とすべて一致することを
  単体テストで固定する（検算: 生年前100 → astro -99。西暦1年 → astro 1 → 年齢 100 ✓。
  前50年 → astro -49 → 年齢 50 ✓）。
- **変換関数・型・年の書式化（「前500」表示・入力パース）は `src/domain/year.ts` に閉じ込める**。
  他のモジュールが `y + 1` のような生の変換を書くことを禁止する（stack-conventions スキルに規約として明記）。
  `StoredYear` と `AstroYear` は TypeScript のブランド型で区別し、取り違えを型エラーにする。
- 入力形式（A-006）: 年入力フィールドは「1600」「-100」「前100」の3表記を受け付けて
  `StoredYear` に正規化する。表示は常に「前100」形式。0 と「前0」は拒否してエラー表示する。

## 結果・影響

- 年齢・列・10年集約のロジックから紀元前の特殊分岐が消え、ドメインロジックの
  テストが単純な算術の検証になる。
- 捨てたもの: 「1つの表現で全レイヤを通す」単純さ。代償として変換の混入リスクを負うが、
  ブランド型 + 単一モジュール集約で機械的に防ぐ。
- 保存スキーマは人間可読（-100 = 前100年）のまま維持され、手動復旧（US-011）を損なわない。
