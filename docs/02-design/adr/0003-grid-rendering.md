# ADR 0003: 年表グリッドの描画方式（DOM仮想化。セルは都度計算で実体化しない）

- 日付: 2026-08-12
- ステータス: 承認済み

## コンテキスト

- グリッドの論理サイズは最大で 人物1000行 × 約3000年列（紀元前1000年〜現在）= 論理300万セル。
  1年単位と10年単位のズームがある（US-002/006/007）。
- 性能要件: 初期表示3秒以内、スクロール・ズーム・検索・絞り込みの応答100ms以内（nfr.md）。
- セルの値（満年齢/仮想年齢）は 表示年と生年から O(1) で計算できる（glossary.md「満年齢」）。

## 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| A: DOM仮想化（可視範囲のセルだけをDOMに実体化。@tanstack/react-virtual の行・列2軸仮想化） | 可視セルは高々 数千個（実測見積: 幅1920px/列44px ≒ 44列 × 高さ900px/行28px ≒ 32行 → 約1400セル + オーバースキャン）で、100ms応答が現実的。テキスト描画・ヒットテスト・ツールチップ・アクセシビリティがDOMの標準機能で済む。ヘッドレスライブラリのため見た目は自由 | スクロール時に窓の再計算が走る（オーバースキャンとメモ化で吸収） |
| B: Canvas 直接描画 | 描画性能の上限が最も高い | テキスト描画・ヒットテスト・ホバー・スクロール連動をすべて自前実装。開発コストと不具合リスクが本規模の要件に対して見合わない |
| C: 仮想化なしの全セルDOM実体化 | 実装が最単純 | 論理300万セルのDOM生成は初期表示3秒・操作100msを確実に破綻させる。不採用 |

## 決定

**選択肢 A（DOM仮想化）** を採用する。

- 行（人物）と列（年）に @tanstack/react-virtual の virtualizer を1つずつ使い、
  可視窓 + オーバースキャン分のセルだけをレンダリングする。
- **セルのデータ構造は作らない**: セル値は描画時に `満年齢(表示年, 人物)` を都度計算する
  （O(1)、`src/domain/year.ts`）。300万セル分の配列・キャッシュを事前構築しない
  （初期表示3秒の主敵はこの種の事前実体化）。
- 行の並び・絞り込み・検索は「人物IDの配列」の変換として `src/domain/query.ts` で行い、
  グリッドは変換済み配列を受け取るだけにする（1000件の配列操作は1ms未満）。
- イベントは年（列）単位に Map<列, イベント[]> へ前集計してイベントレーンに描画する
  （総量5000件の集計は数ms。データ変更時のみ再計算）。
- ズーム切り替え（1年⇔10年）は「列 = 年」を「列 = 10年（astro年の10の倍数境界）」に
  置き換えるだけで同じ仮想化機構を使う。切り替え時は切替前の表示中心年を保持して
  スクロール位置を再計算する（US-007の受け入れ条件）。
- React の再レンダリング抑制: 行コンポーネントを memo 化し、Zustand のセレクタ購読で
  「表示範囲・絞り込み結果が変わった行だけ」更新する。

## 結果・影響

- 捨てたもの: Canvas の描画性能上限。数万行規模になったら再検討する（保証範囲は1000人）。
- 可視範囲外のセルはDOMに存在しないため、「画面に見えているもの」を対象とする機能
  （画像出力 US-012）は可視範囲を正として扱う設計になる（要件と整合: 「表示中の年表範囲」）。
- 純粋なクライアント内描画であり、新しい実行時失敗モード（外部依存・遅延取得）は持ち込まない
  （@tanstack/react-virtual は通常バンドルに同梱。遅延 import はしない）。
- 性能目標はリリース前に保証スケールの実データ（1000人・5000件・3000年）で実測する
  （nfr.md の初期表示3秒・応答100ms。テストフェーズの計測タスクとする）。
