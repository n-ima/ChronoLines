# ADR 0002: データ永続化方式（単一JSONファイル + 原子的書き込み + スキーマ移行）

- 日付: 2026-08-12
- ステータス: 承認済み

## コンテキスト

- 全年表データをローカルにJSON形式で永続化し、再起動後に復元する（US-009）。
- スキーマバージョンを記録し、旧形式は自動移行、未知の新形式は上書きせず停止、
  破損時は初期化せず復旧手段を提示する（US-010）。
- バックアップ・復旧はJSONエクスポート/インポートで行う（US-011、RPO = 最終エクスポート時点）。
- 保証スケール: 人物1000人・イベント総量5000件・年表10個程度（nfr.md、A-003 は2026-08-12に
  ユーザー確認済み = 総量5000件を性能保証範囲とする）。
- 実行形態はローカルサーバー型（ADR 0001）。ファイルの読み書きはサーバーが担う。

## 検討した選択肢

| 選択肢 | メリット | デメリット |
|---|---|---|
| A: 単一JSONファイル（全年表を1ファイル） | 原子的書き込みが1ファイルの rename で完結し、部分破損（年表AとBの不整合）が構造的に起きない。エクスポート形式とほぼ同型。人間が直接読める・コピーできる | 変更のたびに全量書き込み（保証スケールで実測2MB前後 → 問題なし）。数十万件規模には不向き（保証外） |
| B: 年表ごとに1ファイル + インデックスファイル | 書き込み量が年表単位で済む | 複数ファイル間の整合性管理（片方だけ書けた状態）が必要になり、破損モードが増える。5000件規模では利点が出ない |
| C: SQLite | 大規模・部分更新に強い | 「JSON形式でローカル保存」という要件の自然な解釈から外れる。ネイティブ依存の導入とスキーマ管理の重さが本規模には過剰 |

## 決定

**選択肢 A（単一JSONファイル）** を採用する。

- 保存先: `%LOCALAPPDATA%\ChronoLines\chronolines.json`（Windows。環境変数
  `CHRONOLINES_DATA_DIR` で変更可能）。**配布物（アプリのフォルダ）と物理的に分離**し、
  アプリの更新・入れ替え・`git clean` がデータに触れない構造にする（US-010、environment.md
  「保存データは配布物と分離」）。
- 書き込みは**原子的**に行う: 一時ファイル `chronolines.json.tmp` に全量を書き、
  fsync 後に rename で本体を置き換える。書き込み成功のたびに直前の正常版を
  `chronolines.json.bak` として残す（1世代）。
- `schemaVersion`（整数）をルートに必ず記録する。読み込み時:
  - 現行版 → そのまま読み込む。
  - 旧版 → 移行関数チェーン（v1→v2→…）で現行形式へ自動移行する。移行前に
    元ファイルを `chronolines.v<旧版>.bak` として保全してから、移行後データを書き戻す。
  - **未知の新版 → 読み込みを中止し、ファイルには一切書き込まない**。クライアントに
    エラー（コード `NEWER_SCHEMA`）を返し、UIは復旧手段（新しいアプリで開く/インポート）を提示する。
  - **解析不能（壊れたJSON・スキーマ違反）→ 初期化しない**。クライアントにエラー
    （コード `CORRUPT`）を返し、UIはエラー内容とJSONインポートによる復旧手段（US-011）を提示する。
    ユーザーがインポート等で新データを保存する時点で、読めなかった元ファイルを
    `chronolines.corrupt-<タイムスタンプ>.json` に改名保全してから書き込む（黙って捨てない）。
- スキーマ検証は Zod で行い、TypeScript 型・サーバー側検証・インポート検証（US-011）を
  同一定義から導出する（`src/domain/schema.ts` に一元化。詳細設計 data-model.md）。
- 保存タイミング: クライアントが変更のたびにデバウンス（500ms）して全量を PUT する。
  サーバーは書き込みを直列化する。多重タブ対策としてリビジョン番号による楽観ロックを
  併用する（詳細設計 server-api.md）。

## 結果・影響

- 捨てたもの: 部分更新の効率（B/C）。数十万件規模への拡張時はこのADRを見直す
  （保証範囲は5000件。超えても動作は拒否しないが性能保証外）。
- エクスポートファイルは保存ファイルと同一スキーマ（+ エクスポート用メタデータ）になり、
  「保存ファイルをそのままインポート」も成立する = 復旧手順が単純（US-011）。
- **新しい失敗モード = ファイルI/O失敗（ディスク満杯・権限・他プロセスのロック）。受け皿**:
  - フォールバック表示: 保存失敗時、クライアントに常設のエラーバナー（「保存できていません」+
    最終保存時刻）を表示する。編集中データはメモリに保持し、操作は継続できる。
  - エラー境界: 保存APIの失敗はストア層で捕捉し、画面全体を落とさない（機能単位に閉じ込める）。
  - リトライ: あり（次の変更時+手動「再保存」ボタン）。
  - 最終退避手段: サーバーが死んでいてもクライアント単独でJSONエクスポート
    （メモリ上のデータのブラウザダウンロード）が常に可能な設計とする。
