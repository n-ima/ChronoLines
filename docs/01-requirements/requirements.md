# 要件定義書

## 1. 目的・背景

- なぜこのアプリを作るのか（解決したい課題）:
  複数の人物の「生きている時間」を横方向の年表として一覧し、あるイベントが起きた時点で
  各人物が何歳だったかを即座に比較できるようにする。
  （例: 「関ヶ原の戦いのとき、徳川家康は何歳で、伊達政宗は何歳だったか」）
- 誰の・どんな困りごとか:
  歴史上の人物・著名人の年齢を横断比較したいとき、現状は各人の生年を個別に調べて
  都度引き算するしかなく、複数人・複数イベントにまたがる比較が一目でできない。

## 2. スコープ

### やること

- 人物の登録・編集・削除（名前・生年月日（年のみでも可）・没年月日（任意））
- 紀元前の年（生年・没年・イベント年）への対応
- 年表グリッド表示（行 = 人物、列 = 年、セル = その年の満年齢）
- 没後の年のセルは「生きていれば何歳か」（仮想年齢）を色で区別して表示
- イベントの登録・編集・削除（名前・年（月日は任意）・メモ・人物への紐付けは任意）と
  年表上での表示（1つの年に複数登録可・上限なし。表示・性能の保証範囲は100件/年まで）
- 表示する年範囲の自動決定と手動指定
- ズーム（1年単位 ⇔ 10年単位の切り替え）
- 人物の検索（名前）・並び替え（既定: 生年昇順）・タグ/グループによる絞り込み
- データのローカル保存（JSON形式）と、アプリ再起動後の復元
- 複数の年表（例: 「戦国」「幕末」）の作成・切り替え・削除
- データ一式のJSONエクスポート/インポート（バックアップ・復旧の手段）
- アプリのバージョン更新をまたいだデータの引き継ぎ（保存形式の後方互換）

### やらないこと（スコープ外）

- ユーザー登録・ログイン・認証
- 複数人での共同編集・URL共有・サーバー/クラウドへの保存
- ネイティブアプリ化（iOS/Android）
- 多言語対応（日本語のみ）・和暦表記・数え年
- スマートフォン向けの画面最適化（PCブラウザで表示できれば十分）
- 人物情報の外部データベースからの自動取得（Wikipedia連携等）

## 3. 想定ユーザー・利用シーン

- 想定ユーザー像: 開発者本人のみ（単一ユーザー・個人利用）
- 主な利用シーン（Who / When / Where）:
  自分のPC上でローカル実行し、歴史上の人物・著名人（誰でも登録可）を登録して、
  「あのイベントのとき誰が何歳だったか」を調べる・比較する。

## 4. 成功指標

- このアプリがうまくいったと言える基準:
  関ヶ原の戦い（1600年）をイベント登録し、徳川家康（1543年生 → 57歳）と
  伊達政宗（1567年生 → 33歳）の年齢が同一画面で一目で比較できること（US-004）。
- 人物1000人規模を登録しても、表示・操作が実用速度を保つこと（nfr.md 性能要件）。

## 5. ユーザーストーリー

個々の機能要求文は EARS 記法で書き、受け入れ条件の Given/When/Then と対応させる。

### US-001: 人物の登録・編集・削除

- 優先度: Must
- ストーリー: 利用者として、人物を名前・生年月日・没年月日で登録したい。
  なぜなら年表に並べる対象を自由に増やしたいからだ。
- 要求（EARS）:
  - 利用者が人物を登録するとき、システムは名前と生年（年のみ、または年月日）の入力を
    必須とし、没年月日（年のみ、または年月日）を任意入力として受け付けなければならない。
  - もし没年が生年より前ならば、システムは登録を拒否しエラーを表示しなければならない。
  - 利用者が人物を削除したとき、システムはその人物に紐付く個人イベントの扱い
    （併せて削除するか、紐付けを解除して残すか）を確認しなければならない。
- 受け入れ条件:
  - Given 年表が開かれている When 名前「徳川家康」・生年1543を入力して登録する
    Then 年表に家康の行が追加される（正常系・年のみ登録）
  - Given 人物登録フォーム When 生年1600・没年1550 を入力して登録する
    Then エラーが表示され登録されない（異常系）
  - Given 登録済みの人物 When 生年を編集する Then 年表の全セルの年齢が再計算される（正常系）
  - Given 個人イベントが紐付く人物 When その人物を削除する
    Then 「イベントも併せて削除」か「紐付けを解除して残す」かの確認が表示され、
    選択どおりに処理される（正常系・削除確認）

### US-002: 年表グリッドの年齢表示

- 優先度: Must
- ストーリー: 利用者として、行=人物・列=年のグリッドで各人の年齢を見たい。
  なぜなら複数人の年齢を同じ年で縦に比較したいからだ。
- 要求（EARS）:
  - システムは各セルに「その年の誕生日で達する満年齢」（= 表示年 − 生年。
    紀元前をまたぐ場合の計算式は glossary.md「満年齢」参照）を表示しなければならない。
  - システムは生年より前の年のセルを空欄にしなければならない。
  - システムは没年より後の年のセルに仮想年齢（生きていれば何歳か）を表示し、
    生存中のセルとは色で区別しなければならない。
  - システムは生年のセルに 0、没年のセルに生存中と同じ扱いの年齢を表示しなければならない。
  - システムは存命人物の現在年より後の年のセルに仮想年齢を表示し、没後と同じ色区別を
    適用しなければならない（未来のイベントとの年齢比較のため）。
- 受け入れ条件:
  - Given 家康（1543年生・1616年没）を登録済み When 1600年の列を見る
    Then セルに 57 が生存中の表示で示される（正常系）
  - Given 同上 When 1700年の列を見る Then セルに 157 が没後を示す色で表示される（正常系・没後）
  - Given 同上 When 1500年の列を見る Then セルは空欄である（境界・生前）
  - Given 同上 When 1543年・1616年の列を見る Then それぞれ 0・73 が生存中の表示で示される（境界）
  - Given 存命の人物（1980年生）を登録済み When 2100年の列を見る
    Then セルに 120 が仮想年齢の色で表示される（境界・未来年）

### US-003: イベントの登録・表示

- 優先度: Must
- ストーリー: 利用者として、年に紐づくイベントを登録して年表上で見たい。
  なぜならイベントを起点に各人の年齢を調べるのがこのアプリの主目的だからだ。
- 要求（EARS）:
  - 利用者がイベントを登録するとき、システムは名前と年を必須とし、
    月日・メモ・人物への紐付けを任意として受け付けなければならない。
  - システムは1つの年へのイベント登録数に上限を設けてはならない。ただし表示・性能の
    保証範囲は1年あたり100件までとする（nfr.md のスケール前提と整合）。
  - システムはイベントを該当する年の列に対応づけて表示しなければならない。
    人物に紐付くイベントはどの人物のものか識別できなければならない。
  - もし1つの年のイベント数が画面に収まらないならば、システムは件数の要約と
    展開手段（折りたたみ等の具体形は設計で決定）を提供しなければならない。
- 受け入れ条件:
  - Given 年表がある When 「関ヶ原の戦い」を1600年で登録する Then 1600年の列にイベントが表示される（正常系）
  - Given 1600年にイベントが100件登録済み When 年表を表示する
    Then 件数の要約と展開手段によって全件にアクセスできる（境界・保証範囲の上限）
  - Given イベント登録フォーム When 年を空欄のまま登録する Then エラーが表示され登録されない（異常系）

### US-004: イベント時点の年齢比較（コアバリュー）

- 優先度: Must
- ストーリー: 利用者として、あるイベントが起きた年の各人物の年齢を一目で比較したい。
  なぜなら「あのとき誰が何歳だったか」を即座に知ることがこのアプリの目的だからだ。
- 要求（EARS）:
  - 利用者がイベントを選択したとき、システムは該当する年の列と各人物の年齢を
    強調表示等で対応づけて示さなければならない（具体形は設計で決定）。
- 受け入れ条件:
  - Given 家康・政宗と「関ヶ原の戦い」(1600年)が登録済み When イベントを選択する
    Then 1600年の列で家康57歳・政宗33歳が同一画面で確認できる（正常系 = 成功指標）
  - Given 没後の人物を含む年表 When 没後の年のイベントを選択する
    Then その人物は仮想年齢が没後の色で表示される（正常系・没後との組合せ）

### US-005: 紀元前の年への対応

- 優先度: Must
- ストーリー: 利用者として、紀元前に生きた人物やイベントも登録したい。
  なぜなら歴史上の人物の比較が主用途だからだ。
- 要求（EARS）:
  - システムは生年・没年・イベント年として紀元前の年を受け付けなければならない
    （紀元前1000年までを動作保証範囲とし、それ以前も登録を拒否しない）。
  - システムは紀元前の年を「前500」の形式で表示しなければならない。
  - システムは紀元0年が存在しない前提（前1年の翌年は西暦1年）で年齢を
    計算しなければならない（計算式は glossary.md「満年齢」参照）。
  - もし利用者が生年・没年・イベント年・範囲指定のいずれかに0年を入力したならば、
    システムは拒否しエラーを表示しなければならない。
- 受け入れ条件:
  - Given 人物登録フォーム When 生年に「前100」を登録する Then 登録され、前100年のセルに 0 が表示される（正常系）
  - Given 人物登録フォーム When 生年に0年を入力する Then エラーが表示され登録されない（異常系・境界）
  - Given 前100年生まれの人物 When 西暦1年の列を見る Then セルに 100 が表示される（境界・紀元またぎ）
  - Given 同上 When 前50年の列を見る Then セルに 50 が表示される（正常系・紀元前内）

### US-006: 表示する年範囲の自動決定と手動指定

- 優先度: Must
- ストーリー: 利用者として、年表の範囲を自動で出しつつ必要なら手で絞りたい。
  なぜなら普段は全体を見たいが、特定の時代に注目したいときもあるからだ。
- 要求（EARS）:
  - システムは既定で、登録データ（最古の生年・イベント年 〜 最新の没年・イベント年・現在年の遅い方）
    から表示範囲を自動決定しなければならない。
  - 利用者が開始年・終了年を指定したとき、システムはその範囲だけを表示しなければならない。
  - もし指定範囲にどの人物の生存期間も含まれないならば、システムは空の年表と
    その旨の表示を出さなければならない（エラーにしない）。
- 受け入れ条件:
  - Given 1543〜1636年の人物データ When 範囲指定なしで表示する Then 1543年〜現在年が表示される（正常系）
  - Given 同上 When 範囲を1590〜1620年に指定する Then その31列だけが表示される（正常系）
  - Given 同上 When 範囲を1200〜1300年に指定する Then 空の年表と該当なしの旨が表示される（異常系）

### US-007: ズーム（1年単位 ⇔ 10年単位）

- 優先度: Must
- ストーリー: 利用者として、年表を10年単位に畳んで俯瞰したい。
  なぜなら数百〜数千年の範囲を1年刻みで横スクロールするのは現実的でないからだ。
- 要求（EARS）:
  - システムは列の単位を1年と10年で切り替えられなければならない。
  - 10年単位の間、システムは各人物の生存期間が帯として視認できる表示を
    維持しなければならない（10年帯での年齢・イベントの集約表現は設計で決定し、
    モックアップでユーザー確認する。前提 A-004）。
- 受け入れ条件:
  - Given 1000年分の年表 When 10年単位に切り替える Then 列数が約1/10になり生存帯が視認できる（正常系）
  - Given 10年単位表示 When 1年単位に戻す Then 切り替え前に表示していた範囲の中心の年が、
    切り替え後の表示範囲に含まれている（正常系）

### US-008: 人物の検索・並び替え・タグ/グループ絞り込み

- 優先度: Must
- ストーリー: 利用者として、1000人規模の中から目的の人物の行をすぐ見つけたい。
  なぜなら行が多いと目視で探すのは不可能だからだ。
- 要求（EARS）:
  - 利用者が人物名（部分一致）で検索したとき、システムは該当する人物の行へ
    移動・強調表示しなければならない。
  - システムは既定で人物を生年の昇順に並べなければならない。利用者が手動で変更した
    並び順は保存データに含め、アプリ再起動後も復元しなければならない。
    手動並び替え後に追加された人物は末尾に置き、利用者はいつでも既定順（生年昇順）へ
    戻せなければならない。
  - 利用者が人物に0個以上のタグ（例: 「戦国」「幕末」）を付与でき、
    タグで表示する人物を絞り込めなければならない。
- 受け入れ条件:
  - Given 1000人登録済み When 「家康」で検索する Then 該当行が表示範囲に現れ強調される（正常系）
  - Given 「戦国」タグの人物30人を含む1000人 When 「戦国」で絞り込む Then 30行だけが表示される（正常系）
  - Given 検索語に該当者がいない When 検索する Then 「該当なし」が表示され表示は変化しない（異常系）
  - Given 手動で並び替えた年表 When アプリを再起動する Then 並び順が復元されている（正常系・永続化）

### US-009: データのローカル保存と複数年表の管理

- 優先度: Must
- ストーリー: 利用者として、登録したデータをローカルに保存し、テーマ別の年表を
  切り替えて使いたい。なぜなら用途（戦国・幕末など）ごとに独立した年表を持ちたいからだ。
- 要求（EARS）:
  - 利用者が人物・イベント・年表を変更したとき、システムはその変更をローカルの
    JSON形式データとして永続化し、アプリ再起動後に復元しなければならない
    （保存先の具体形 = ファイル/ブラウザストレージ等は設計で決定。前提 A-001）。
  - システムは複数の年表の作成・名前変更・切り替え・削除ができなければならない。
  - 利用者が年表を削除するとき、システムは確認を求めなければならない。
- 受け入れ条件:
  - Given 人物を登録した When アプリを再起動する Then 登録内容が復元されている（正常系）
  - Given 年表「戦国」「幕末」がある When 切り替える Then それぞれの人物・イベントだけが表示される（正常系）
  - Given 年表が1つ When それを削除しようとする Then 確認が表示され、承諾しなければ削除されない（異常系）

### US-010: バージョン更新をまたぐデータ引き継ぎ

- 優先度: Must
- ストーリー: 利用者として、アプリを新バージョンに更新しても登録済みデータを
  そのまま使いたい。なぜならデータは長期に蓄積する資産だからだ。
- 要求（EARS）:
  - システムは保存データにスキーマバージョンを記録しなければならない。
  - アプリが旧バージョンの保存データを読み込んだとき、システムは現行形式へ
    自動移行して読み込まなければならない（データを消失させてはならない）。
  - もし保存データが未知の（より新しい）バージョンならば、システムはデータを
    上書きせず、エラーを表示して停止しなければならない。
  - もし起動時に保存データが読み込み不能（破損・形式違反）ならば、システムは
    既存データを上書き・初期化せず、エラーとJSONインポート（US-011）による
    復旧手段を提示しなければならない。
- 受け入れ条件:
  - Given 旧形式の保存データ When 新バージョンで開く Then 全データが移行され表示される（正常系）
  - Given 新形式の保存データ When 旧バージョンで開く Then 上書きされずエラーになる（異常系）
  - Given 壊れた保存データ When アプリを起動する Then 既存データは初期化されず、
    エラーと復旧手段（インポート）が提示される（異常系・破損）

### US-011: JSONエクスポート/インポート（バックアップ・復旧）

- 優先度: Must
- ストーリー: 利用者として、データ一式をJSONファイルとして取り出し・取り込みたい。
  なぜならバックアップと復旧はこの手段で行うと決めているからだ。
- 要求（EARS）:
  - 利用者がエクスポートを実行したとき、システムは選択した年表（または全年表）の
    データ一式を1つのJSONファイルとして出力しなければならない。
  - 利用者がインポートを実行したとき、システムはファイル内容を検証し、
    既存データへの影響（置き換え/追加）を確認してから取り込まなければならない。
  - もしインポートファイルが不正（形式違反・壊れたJSON）ならば、システムは
    既存データを変更せずエラーを表示しなければならない。
- 受け入れ条件:
  - Given データ登録済み When エクスポート→全削除→インポートする Then 元の状態に復元される（正常系 = 復旧手順）
  - Given 壊れたJSONファイル When インポートする Then エラーが表示され既存データは無傷（異常系）

### US-012: 年表の画像出力・印刷

- 優先度: Could
- ストーリー: 利用者として、表示中の年表を画像や印刷で残したい。
  なぜなら人に見せたり資料に貼ったりできると嬉しいからだ。
- 要求（EARS）:
  - 画像出力機能を持つ場合、システムは表示中の年表範囲を画像ファイル（PNG等）として
    保存できなければならない。
  - 印刷はブラウザ/OS標準の印刷機能で代替し、専用機能は作らない（要求は画像出力のみ）。
- 受け入れ条件:
  - Given 表示中の年表 When 画像出力する Then 表示範囲が画像ファイルとして保存される（正常系）

## 6. 制約条件

- 納期・予算: 制約なし（個人開発）。
- 技術: 指定なし（設計フェーズでエージェントが提案し、ユーザーが選定する）。
- 実行環境: ユーザーのWindows PC上でのローカル実行のみ（ホスティングなし）。
  詳細は [environment.md](environment.md)。
